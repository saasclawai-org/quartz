# Quartz L2 — Channel Payment Design

> **One-liner:** Hub-and-spoke payment channels with eltoo-style state and PUF-optional identity — consensus-native, no scripting, designed for 8MB-flash microcontrollers.

**Status: DESIGN — nothing here is built.** All performance figures are *projected*, pending bench measurement (see §8). Per VALUE.md's rule: measured, not marketed.

---

## 1. Why L2, and when

The L1 is deliberately tiny: 10 txs / 30s block ≈ 0.33 TPS. The mesh fork adds micro-payment demand (relays paid per byte, sensors per reading, inference per call) that must never touch consensus. 

**Trigger to build:** real micropayment volume at the mesh fork. Not before. The Helium lesson applies to L2 as much as to radio — no infrastructure ahead of demand.

**What exists today (proto-L2):** the inference escrow (request → hold → payout) is a custodial off-chain ledger settled on-chain. Honest label: trusted-operator, simulator-grade. The channel design below is its decentralized replacement.

## 2. Design principles

1. **No scripting.** Today's chain is single-sig; outputs are address bytes. Lightning's complexity comes from Bitcoin Script. We add three *native* tx types instead — a few hundred lines of validation, not a VM.
2. **eltoo-style, not punish-style.** Lightning's revocation storage (keep every old secret forever) is hostile to 8MB flash and NVS wear limits. Newest-signed-state-wins-after-delay needs no punishment transcripts. Cost: stale-close attempts are possible → watchtowers (§6).
3. **Board-first budgets.** Channel state < 1KB RAM per counterparty. Updates live in RAM; checkpoint to NVS every 64 updates or on close (safe: both signatures exist).
4. **Hub-and-spoke first, routing later.** 20–50 miners don't need pathfinding. One channel per board to a hub (reference node, Pi, or well-connected peer). Multi-hop HTLCs only if the mesh grows into a real graph.

## 3. L1 forward-compat (the cheap part, do now)

Add a 1-byte tx type to the tx envelope **before the mesh fork**, so mainnet genesis has it from day one:

| Type | Name | Meaning |
|---|---|---|
| 0x00 | `transfer` | Today's tx (default; old parsers unaffected) |
| 0x01 | `channel_open` | Lock funds to (partyA, partyB, timeout) |
| 0x02 | `channel_update` | Off-chain state (never on-chain except in dispute) |
| 0x03 | `channel_close` | Cooperative (both sigs, instant) or unilateral (delayed claim) |

Validation rules for 0x01–0x03 activate at the mesh fork; until then the node accepts and ignores them. This is the only L1 change needed now.

## 4. Channel lifecycle

```
OPEN    A→chain: channel_open{A_addr, B_addr, funding_sats, timeout=720 blocks}
        UTXO locked; only channel_close can spend it.

UPDATE  A↔B off-chain: {seq, balA, balA} + sigA + sigB      (~210 B, 1 radio frame)
        Both sign the new state. seq strictly increases. No chain contact.

CLOSE   cooperative: both sigs on final state → mined next block, instant.
        unilateral: publish latest update; counterparty (or watchtower) can
        publish a higher-seq update within 720 blocks (6h @30s). After the
        window, balances pay out. Stale close = you lose the race, not coins.
```

**State size:** seq(8) + 2×balance(16) + 2×Ed25519 sigs(128) + overhead ≈ **210 B** — fits one ESP-NOW frame.

## 5. Wire formats

- `update_msg` = `0x02 ‖ chan_id(32) ‖ seq(8) ‖ balA(8) ‖ balB(8) ‖ sigA(64) ‖ sigB(64)`
- Signed payload = everything except the signatures.
- Checkpoint blob (NVS) = latest `update_msg` + peer address + funding txid ≈ **< 300 B**.

## 6. Watchtowers

Pi nodes already sync the chain; watching for stale closes is nearly free: see a `channel_close` with seq < your latest → publish the higher-seq update.

- Delay window 720 blocks (6h) — a board can be offline overnight and still justice.
- Watchtower fee: small QZ per guarded channel per week → another genuine utility sink.
- A watchtower needs only: `chan_id`, latest `seq`, and a pre-signed counter-update per client (~350 B/channel) — **no balances, no keys** — so a malicious watchtower can defend you but cannot rob you.

## 7. PUF-bound channels (optional, on-brand)

Channel state may be countersigned with the hardware identity (same Ed25519 key the PUF enrollment derived). Effect: a stolen phone *with* the seed phrase still can't move a board's channel state the board never agreed to. This ties L2 to the same unclonable-silicon moat as the rest of the stack. Phones/PWAs opt out (soft keys only).

## 8. Performance targets — projected, pending measurement

Ed25519 sign dominates every path (not radio, not blocks):

| Path | Bottleneck | Projected rate | Latency |
|---|---|---|---|
| Board ↔ board (ESP-NOW) | 2 signs ≈ 40ms (S3) | ~20 updates/s/channel | ~50 ms |
| Board ↔ hub (WiFi) | sign-bound | ~30/s/board | ~30 ms |
| Phone/PC ↔ hub (TCP) | RTT-bound | ~1,000+/s/channel | ~10 ms |
| Hub aggregate (Pi 4) | verify: ~1–2K/core | ~5,000/s all channels | — |

Per-channel ≠ global: rates are per *relationship* and don't compete (N private lanes vs. one shared L1 bus). 50 boards × hub channel ≈ 1,500/s aggregate.

**Do not quote publicly until §9 lands.** These are silicon-math projections.

## 9. Bench benchmark mode (v072, cheap)

Extend `firmware-espnow-test` with a channel-update benchmark: two boards run N sequential eltoo-style updates (sign→send→verify→countersign), printing updates/sec and verify/sec per board, at several distances. ~1 day of work, reuses the bench harness; turns §8 from projected to measured before the mesh fork.

## 10. Implementation scope (at mesh fork)

- **Node (testnet.py):** tx types 0x01–0x03 validation, channel UTXO rules, close windows.
- **Firmware (ESP-IDF):** channel state machine + NVS checkpoint + ESP-NOW transport (~600 LOC est).
- **Android + PWA:** channel state machine, hub connection over TCP (~shared core with firmware logic re-implemented per platform).
- **Pi bundle:** watchtower module (subscribe chain, store guard blobs, auto-counter stale closes).

The multi-platform state machine is the real cost — and the reason this ships with the mesh fork, not before.

## 11. Non-promises

- No routing/HTLCs until the mesh is a graph, not a star.
- No anonymity claims beyond L1: channel updates are already private (two parties only), but hub topology concentrates metadata at hubs — the radio transport is what removes IPs, not the channel layer.
- No "Lightning for ESP32" marketing. This is a small, auditable state machine — the whole point.
