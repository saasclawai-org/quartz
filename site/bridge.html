Quartz Bridge

Turn your idle Helium hotspot into a Quartz mesh relay. Bridge blocks and transactions between the gateway and ESP32 miners over LoRa — no new hardware needed.

Got a Helium hotspot earning $0.05/month?

Your Bobcat, RAK, or SenseCAP has a Linux board, a LoRa concentrator, storage, and WiFi — everything a Quartz bridge node needs. The hardware is already deployed on a rooftop with power and an antenna.

How It Works

The bridge relays data between the online gateway and offline ESP32 miners.

Quartz Gateway (VPS) ←── TCP P2P ──→ Bridge (Helium Hotspot) ←── LoRa Mesh ──→ ESP32 Leaf Miners Gateway ──── blocks, work templates ────→ Bridge ──── LoRa ────→ Miners Miners ──── found blocks, txs ─────→ Bridge ──── TCP ─────→ Gateway
📥

Gateway → LoRa

Receives new block headers and work templates from the Quartz gateway over TCP. Relays them to ESP32 miners over LoRa (2–15km range).

📤

LoRa → Gateway

Receives found blocks and transactions from ESP32 miners via LoRa. Submits them to the gateway for network inclusion.

📡

Mesh Relay

Gossips packets between miners using TTL-based flooding. Store-and-forward for peers that were offline. Beacons every 60s.

Quick Install

Three steps. Takes about 5 minutes. Reversible.

1SSH into your hotspot

Find your hotspot's IP address (check your router's DHCP list or scan for port 22).

ssh root@<hotspot-ip> # Bobcat default password: bobcat # RAK default: root # SenseCAP: check manufacturer docs

If SSH is disabled, you may need to enable it via the hotspot's diagnostic tool or web UI. Some hotspots also have a serial console via USB.

Check Python 3 is available: python3 --version. If not: opkg install python3 (OpenWrt) or apt install python3 (Debian).

2Download and run the installer

One command. The installer auto-detects your hotspot model, backs up the Helium packet forwarder config, and reconfigures it for Quartz.

curl -sSL https://quartzchain.net/bridge-install.sh | bash

Or with custom options:

curl -sSL https://quartzchain.net/bridge-install.sh | bash -s -- --gateway quartzchain.net --region EU868

The installer will:
1. Download the bridge code from our server
2. Detect your hotspot model (Bobcat, RAK, SenseCAP, or generic)
3. Back up the Helium packet forwarder config to /opt/quartz-bridge/backup/
4. Reconfigure the packet forwarder to send to the bridge (UDP 1738)
5. Install the bridge daemon to /opt/quartz-bridge/
6. Create and start systemd services

3Verify it's running

journalctl -u quartz-bridge -f # You should see: # [INFO] Connected to gateway (height=N, hash=...) # [INFO] Beacon sent (height=N, peers=0) # [INFO] LoRa RX loop started

That's it. The bridge is now listening for ESP32 miners on LoRa and relaying data to the Quartz gateway.

⛏️ Flash an ESP32 miner

Now flash an ESP32 with Quartz firmware and power it on near the hotspot. It'll pick up the LoRa mesh and start mining.

Why This Works

Helium hotspots are already Quartz bridge hardware — they just don't know it yet.

🏗️

Right Hardware

Linux SoC (Pi CM4 or ARM) runs the Python bridge daemon. SX1302 LoRa concentrator handles radio. SD card stores the chain. WiFi/Ethernet connects to the gateway. It's the exact bridge node spec from the Quartz roadmap.

🔄

Smart Reuse

The bridge uses the hotspot's existing Semtech packet forwarder binary — we just redirect its UDP traffic from Helium's servers to the bridge process. No board-specific SPI drivers needed. Works on any SX130x hotspot.

📊

Better Radio

The SX1302 concentrator listens on 8+ channels simultaneously. The ESP32's SX1276 is single-channel. A single Helium hotspot acting as a bridge can serve many more leaf miners than an ESP32 bridge could.

♻️

Fully Reversible

The installer backs up the original Helium config. To revert: stop the Quartz services, restore the backup, restart Helium. Your hotspot goes back to mining HNT (such as it is).

Monitoring

Check bridge health and mesh stats.

# Bridge logs (live) journalctl -u quartz-bridge -f # Packet forwarder logs journalctl -u quartz-lora-fwd -f # Check if connected to gateway journalctl -u quartz-bridge | grep "Connected to gateway" # Service status systemctl status quartz-bridge quartz-lora-fwd

Reverting to Helium

Changed your mind? Fully reversible.

sudo systemctl stop quartz-bridge quartz-lora-fwd sudo systemctl disable quartz-bridge quartz-lora-fwd # Restore original packet forwarder config sudo cp /opt/quartz-bridge/backup/*.bak.* /opt/<hotspot>/ # Restart original Helium services sudo systemctl start helium-miner # or lora-pkt-fwd

Your Helium backup configs are saved in /opt/quartz-bridge/backup/ during installation.

FAQ

Can the hotspot mine Quartz?

No. Quartz mining requires an ESP32 with SRAM PUF attestation — the block hash includes a key derived from the physical silicon. A Linux-based hotspot can't produce PUF attestations. The bridge relays for miners; it doesn't mine.

Does the bridge earn rewards?

The Quartz roadmap allocates a 10% mesh relayer share of every block. This is currently deferred (set to 0%) until the LoRa mesh fleet is live and relay-share accounting is validated in-block. When that fork activates, bridge nodes will earn relayer rewards on every block mined by ESP32s in their LoRa range.

Will this break my Helium mining?

While the Quartz bridge is running, the hotspot's packet forwarder is pointed at the bridge instead of Helium's servers. Helium mining stops. The installer backs up the original config and the revert process restores it. You can switch back and forth.

What LoRa frequency does Quartz use?

Same as the ESP32 firmware: 915 MHz (US), 868.1 MHz (EU), 923.2 MHz (Asia), 470 MHz (China), 865 MHz (India). Set with the --region flag during install. Must match the frequency of your ESP32 miners.

How many ESP32 miners can one bridge serve?

The SX1302 concentrator can listen on 8+ channels simultaneously, so it can handle many more concurrent miners than a single-channel ESP32 bridge. Practical limit depends on LoRa airtime and packet frequency, but dozens of miners in range is feasible.

Do I need internet on the hotspot?

Yes — the bridge connects to the Quartz gateway over TCP. WiFi or Ethernet backhaul is required. For truly off-grid deployment, you'd need a bridge with satellite or a local gateway, but that's a future use case.

Is the bridge open source?

Yes — MIT licensed, same as the rest of Quartz. The bridge daemon is pure Python 3 with zero external dependencies.
